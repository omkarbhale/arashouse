# Acceptance: the whole lease cycle on the host for `12sp9`

Ticket 35. The promise, proven end to end once for one flavor: **a returned slot is wiped, and the next lease is clean.**
The captain's words:

> "The philosophy is that Aras are disposable, and anything durable should be taken out by whoever took the lease before
> giving it back."
> "It doesn't necessarily clean it up ON freeing the lease, but the worker can assume it has cleaned up."

## How it runs

`test/host/e2e-cycle.ts` is the procedure; `test/host/e2e-12sp9.test.ts` runs it twice in a row, and only when asked
(`ARASHOUSE_TEST_E2E=1`, the variables are in its header). It runs from WSL as the worker, non-elevated, against the
installed broker, and drives the built CLI (`dist/`) as a worker would. Every step is a line in
`<ARASHOUSE_E2E_OUT>/cycle-<n>.log` and `.json`.

It dirties a lease only as a leaseholder can: logged in as `root` with the lease's password, from WSL. The tree is written
by a server Method of the leaseholder's own (`methodCode()`), which runs as the slot's pool identity; a provision grants
that identity modify on the slot folder (`docs/provision.md`), so a leaseholder's server code can write anywhere in its
slot's tree. The worker's own grant on `slots\` is read only, and it has none on `golden\` or `vaults\`, so the vault is
counted by the same Method on the next lease.

The golden backup's `root` password is used only by `test/host/login-check.ps1` (one OAuth grant, the password decrypted
inside that Windows process from the captain's DPAPI file, printing only `login: ok` or the server's refusal), which
firstmate approved to run non-elevated. Every password in the cycle is a `Secret`, so `redact` replaces it in the record.

## Divergences found, and fixed here

- **A killed reset worker quarantined a healthy slot** (ticket 14). The broker does not know its caller died, so the dead
  worker's verb (here `quiesce`) runs on to its end and holds the slot's lock (`SlotLocks`). The reset that recovers the
  slot met "slot 12sp9-01 is being provisioned, destroyed, started, stopped or reset already" (`Retryable`) twice within
  1.5 s and quarantined it. Now a step that gets that answer (`isSlotBusy`, `src/host/errors.ts`) waits for the verb to
  end, polling every 2 s for up to 15 minutes, without using up its retry (`src/core/reset.ts`, `docs/reset.md`). Run 5
  recovered the slot both ways.
- **`BrokerHost` did not refuse a bad staged path** for the three verbs the broker does not have yet (`deployCode`,
  `restoreDatabase`, `backupDatabase`: tickets 40, 39, 43): it answered `Unreachable` ("no verb yet") where `FakeHost`
  answers `Refused`, so the contract suite's staged-path test failed. It now runs `assertStagedPath` first, as the fake
  does.
- **No health check could log in** until the golden backup's `root` password was stored: the new `storeOotbRoot` verb and
  `scripts/store-ootb-root.ps1` (`docs/health.md`).

## A known limit: the old lease's access token

Found by ticket 36 (`docs/e2e-23.md`), and measured here too (2026-10-28): root's access token from a `12sp9-01` lease,
issued before the return, was still answered on `12sp9-01` after the reset had finished. The password the token came from
is dead, but the token is a self-contained JWT (`accessTokenLifetime` 3600 s) signed with the OAuth certificate every slot
of the flavor copies from golden, and it names root, whose id is the same in every restore of the golden backup. Nothing
the reset restores holds it, so the previous leaseholder can act as root on the next lease of the same slot until the
token expires. Another slot refuses it: the token names its slot's database ("Database configuration was not found").
The cycle does not check it; ticket 36's cycle records the probe as an observation. A per-reset OAuth signing certificate
is a map ticket of its own.

## Findings that change nothing

- **A lock the worker holds on a slot file keeps nobody out.** The ticket's quarantine route was a file lock held on a
  slot file. Opened by the worker with `FileShare.None` from WSL, a slot file's handle still let any other reader in and
  did not stop the broker's mirror and config writes: the first attempt's reset simply succeeded. The same lock on a file
  in `staging\` (where the worker has modify) kept everyone out. Measured, not explained; in `slots\` the worker may only
  read. So the cycle holds the lock as a leaseholder would: its Method starts a process (`mode` `lock`) as the pool
  identity that opens a new file in `Innovator\Client` with no sharing for 150 s. Its command line does not name the slot
  folder (the path is in its environment), so the quiesce, which ends the slot's processes by their path or command line,
  does not end it; it outlives the pool stop.
- **That reset is quarantined at the first attempt, not after two.** robocopy cannot delete the locked extra file but
  still exits below 8, and the tree step's `fast` verify then finds the extra file, which is a `Quarantine` error by
  ticket 30's design ("any difference: Quarantine"). The slot is quarantined with the file named and never handed out;
  `repair` clears it once the process has ended.
- **The broker's audit log** is readable only elevated (`logs\`). At the end of each cycle, after its leases are returned
  and reset, the cycle writes its lease passwords to `staging\e2e-<flavor>\leak-cycle-<n>.dpapi`, one
  `ConvertFrom-SecureString` line each (this Windows user's DPAPI), through a `powershell.exe` that reads them on stdin
  only. `test/host/audit-leak-check.ps1`, run elevated by firstmate's gate, decrypts them in memory, counts their matches
  in every file under `logs\` (the audit log and the service log), prints only file names, counts and a total, and deletes
  the file. Run 6 (one more whole cycle from the same code, 2026-10-27 23:28Z, every check passed) sealed its four lease
  passwords; the gate's elevated run of the script (SHA-256 verified, exit 0) printed `broker-20261027.log: 0`,
  `broker-service.log: 0`, `total: 0`, and deleted the file. So none of the cycle's lease passwords is in the broker's
  audit log or its service log either.
