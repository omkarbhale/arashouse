# Spike 07: Release 23 (14.0 SP9) against the 12 SP9 baseline

Recorded 2026-10-27 on the captain's laptop (the host of [spike 05](spike-05-12sp9-baseline-and-clone.md): Windows 11, IIS 10, SQL Server 2019,
.NET Framework 4.8.1), with throw-away names only (`ah-spike-23-*`, `arashouse_spike_23_*`, `C:\aras_installations\spike\`). Media: the Release 23
CD image zip in the main checkout's `media/23/`, unpacked to `staging\23\cd\`. Scripts: `spike/09` to `spike/30` and `spike/90` with `-Flavor 23`,
run through firstmate's elevated gate; the engine smoke test ran unelevated from WSL. Raw results (names, booleans, counts; no secrets) were
`C:\aras_installations\spike\out\*-23*.json`. Everything below is measured or read, not assumed.

### The questions

1. **Prerequisites.** The MSI checks only .NET Framework 4.7.2 or newer. The 14.0.9 code tree is `net6.0` throughout (Innovator server and client,
   OAuth, Vault), so the host needs the ASP.NET Core 6 runtime and the ASP.NET Core Module V2, which the 6.0.36 Hosting Bundle provides. The host
   already has it (shared runtimes 2.1.15, 6.0.36, 8.0.31, 10.0.9; module 16.0.24290). Nothing was installed for this spike.
2. **IIS and config files.** Six applications instead of seven (no NotificationServer); the Innovator, Client and Server pools change from
   .NET 4.0 to no managed runtime; the eight config files a clone edits are the same as 12's. See the table.
3. **Version and patch.** The installed `Aras.Server.Core.dll` reads `14.0.9.36073`, as does the MSI's File table. The patch zip is an Aras Update
   package (`package.config`: `ArasUpgradePackage`, version `14.0.9.36073`, "Release 23 (14.0.9)") whose version check accepts only code trees
   whose `Client\scripts\include\rev.inc` is 14.0.0 to 14.0.8: it upgrades an older 14.0 to the build the MSI already installs. **The baseline
   does not include the patch.** (The captain's own `Aras\Innovator` install, which the ticket meant to compare against, no longer exists: it was
   removed during spike 05.)
4. **Licence.** `30-licence-reuse.ps1` read each key from an installed config (read only, never printed) and wrote it into both spike slots:
   - no key: both slots refuse login (`Missing lic_key directive in the control file`), as on 12;
   - **the 12.x key (Aras12's) is refused** by both 14.0.9 slots: `License Key is invalid.`;
   - **the 14.0 SP18 key (Aras28's, type `Unlimited`, with an activation key) is accepted by both 14.0.9 slots**, and still after a second recycle
     and after a full stop and start of all pools.

   So a key is bound to its release line, not to the service pack: one 14.x key serves every 14.0 slot, the captain's SP9-specific key is not
   needed, and the tool asks for one key per line (12.x and 14.x so far; 35 is ticket 08).
5. **Engine smoke.** `aras-pkg export --engine 14.0.7 ItemType:<Part's id>` as `root` (password from `ARAS_PASSWORD`) succeeded against both
   slots: the login gate and the version probe accepted server `14.0.9.36073`, and the item was written to `PLM/Import/ItemType/Part.xml` with an
   `imports.mf`. The CLI must run under Windows `node.exe` (or anywhere `localhost` is the host): the server's OAuth discovery answers with
   `http://localhost/...` URLs, which WSL does not reach. It also cannot write to a `\\wsl.localhost\` path, so its output went to a `C:` folder.
6. **Restore and fix-ups.** `CoreAndSolutions140.bak` restores in 1.3 s; the fix-ups are 12's minus one: remap `innovator` and
   `innovator_regular` to the slot's logins with `ALTER USER ... WITH LOGIN` (no orphaned user is left), no owner change (every table is in
   the `innovator` schema), no role membership to restore, no vault URL to patch. `Utilities\fix_innovator_user.sql` is two
   `sp_change_users_login 'Auto_Fix'` calls, which link each user to the server login of the same name: on this host that is the machine-wide
   `innovator` login of the captain's own databases, so the script is not usable for per-slot logins; `ALTER USER ... WITH LOGIN` is its per-slot
   form. The CD's three post-restore scripts are the same in 12 SP9 and Release 23 (spike 05).

### Changes for later tickets

- **19 (edit list).** The 14.0 list is the same eight files and edits as 12's. There is no `ConversionServerConfig.xml` (the conversion server is
  not installed) and no agent config (no agent installed).
- **24 (baseline builder).** One licence key per release line: `12sp9` uses a 12.x key, `23` a 14.x key; a 14.0 SP18 key works. Record the
  ASP.NET Core 6 Hosting Bundle as a `23` prerequisite in `flavor.json`. If the builder installs the agent (`INSTALL_AGENT_SERVICE=1`) it must
  set `AS_FOLDER` to a name of its own: the 14.0 MSI aborts when `ArasInnovatorAgent_<AS_FOLDER>` exists, and the default `AS_FOLDER` is
  `ArasInnovatorAgent`, which the captain's installs may use.
- **25 (slot templates).** `iis.json` for `23`: six applications, five of them in pools with no managed runtime. Each running ASP.NET Core
  application is its own `Aras.Server.exe` or `Aras.Client.exe` process next to `w3wp.exe`, so per-slot memory must be measured by process tree,
  not by `w3wp.exe` alone (ticket 06's measure and ticket 38). The MSI's 8 h idle timeout is replaced by the short one the ticket plans.
- **26 (baseline 23).** No patch in the baseline; the expected version stays `14.0.9.36073`, now confirmed from the MSI and the installed tree,
  not from the captain's (removed) install; the engine check works as described, run where `localhost` reaches IIS.

## Surprises

1. **The Innovator server is no longer an IIS-hosted .NET Framework application.** IIS only proxies to `Aras.Server.exe`/`Aras.Client.exe`; the
   cold first request of a clone took 37 s against 12 s on 12 SP9.
2. **The 12.x key is refused by 14.0, but a key of a different 14.0 service pack is accepted.** The three different keys found on the host
   (design report) are not all needed: one per release line is.
3. The silent install generates an OAuth certificate password that is not a row of the Property table; `10-baseline-install.ps1` now always lists
   it (and the SQL passwords) in `MsiHiddenProperties`, so it is not written to the MSI log.

## Teardown

`90-teardown.ps1` (640 s) uninstalled both spike products (`msiexec /x`, `REMOVE_DATABASES=0`, exit 0 each), removed 18 applications and 18 pools,
dropped both databases, four logins and the two `master` users, and removed the spike folders; nothing with a spike prefix is left (`leftover`
all 0). Pre-flight afterwards: `denyListUnchangedSinceBaseline: true`. The unpacked CD media stays in `staging\23\` for ticket 26.
