# Acceptance: the lease cycle on the host for `23`

Ticket 36. Ticket 35's procedure (`docs/e2e-12sp9.md`) for flavor `23`: Release 23, server `14.0.9.36073`, libs-js
engine `14.0.7`. The promise is the same, **a returned slot is wiped, and the next lease is clean**, and this flavor adds
the 14.0 OAuth server's runtime state (design report 5.2: `OAuthServer\App_Data\*.sqlite*`, `key-*.xml`).

## How it runs

`test/host/e2e-23.test.ts` runs `test/host/e2e-cycle.ts` twice in a row for `23`, only when asked (`ARASHOUSE_TEST_E2E=1`,
the variables are in its header), from WSL as the worker, non-elevated, against the installed broker. It is ticket 35's
cycle with three options:

- `engine: "14.0.7"`: libs-js `aras-pkg` (import-export-libs-js `99c19b98`, the commit spikes 07 and 26 used) exports and
  imports through `arashouse run --lease`, from WSL, at the lease's own URL. With `--json` its summary names the server
  its version probe found, which must be the registry's build (step 2, for every flavor now).
- `oauthState: true`: the leaseholder also asks for a refresh token (`offline_access`, which `IOMApp` may ask for), which
  the OAuth server keeps in `OAuthServer.sqlite`'s `PersistedGrants`, and its Method writes a `key-arashouse-e2e-<tag>.xml`
  (an XML element the key ring ignores) and an `arashouse-e2e-<tag>.sqlite` into `OAuthServer\App_Data`. On the next lease
  the cycle checks that both files are gone, that the `key-*.xml` files equal the provisioned ones (SHA-256, not printed),
  that a copy of the SQLite file (with its write-ahead log) holds no grant of the lease, and that the OAuth server refuses
  the old refresh token.
- `lockHolder: "worker"`: step 8's lock (below).

A `get` the cycle expects to lease at once now passes `--wait 300`, for every flavor: it leases a free slot at once, and
waits out a dip of the host's free RAM under `min_free_ram_mb`, which on this laptop the rest of its work causes.

Step 3 also records the leased slot's memory, by process tree: the slot's pools' `w3wp.exe` (from IIS's `W3SVC_W3WP`
counter instances, `<pid>_<pool>`, since a worker cannot read another identity's command line), their children and the
slot's agent service.

## Divergences from `12sp9`, and fixed here

- **The 14.x client writes a data-protection key at its first request.** `Innovator\Client` is an ASP.NET Core
  application from 14.0, and it writes `App_Data\key-<guid>.xml` the first time it serves after a start. The golden build
  never requests the client, so golden has no such file, and every `23` health check failed `tree` ("1 extra"): every
  reset would have quarantined its slot. `Innovator/Client/App_Data` and `Innovator/Server/App_Data` `key-*.xml` are now
  runtime files (`RUNTIME_DIRS`, `docs/manifest.md`), as OAuth's already were. The server's key is in golden; it is a
  runtime file too, because the server writes a new one when golden's expires (ASP.NET Core's default key lifetime is 90
  days), which would otherwise quarantine every slot a quarter after the golden build. The reset's mirror removes the
  client's key with everything else golden lacks, and restores the server's.
- **The leaseholder's Method found the tree one level off.** A 12.0 server Method runs in an ASP.NET application rooted
  in `Innovator\Server`; a 14.x one runs in `Aras.Server.exe`, whose base directory is `Innovator\Server\bin`. The cycle's
  Method now steps out of `bin` (a test fix; run 1 stopped there).
- **A leaseholder's server-side process does not outlive the quiesce on 14.x.** Ticket 35's quarantine route was a process
  the Method starts as the pool identity, holding a file open with no sharing. On `23` that process was gone by the
  mirror and the reset simply succeeded (run 2), probably because 14.x's out-of-process server and its children run in
  their pool's job; nothing of the leaseholder's runs on after the pool stops, which is what a reset wants. So for `23`
  the Method only writes the file, and the worker's own Windows process (`powershell.exe`, the path on its stdin so that
  its command line names no slot folder) holds it open, as a leaseholder's editor or tool could. robocopy cannot delete
  it, the tree step's `fast` verify finds it, and the slot is quarantined at the first attempt, as on `12sp9`.
- **The cycle could leave a lease behind** when a `get` it expected to be refused succeeded (run 2's step 8): every lease
  the cycle still holds is now returned at its end, whether it failed or not.
- **Not a divergence: the engine runs from WSL.** Spike 07 ran `aras-pkg --engine 14.0.7` under Windows `node.exe`
  because "the server's OAuth discovery answers with `http://localhost/...`". A slot's does not: its OAuth server builds
  every discovery URL from the request's host (`http://172.19.0.1/ah-23-01/OAuthServer/connect/token`), and the Innovator
  server's `OAuthServerDiscovery.aspx` answers with the request's host too. So export and import through `run --lease`
  from WSL passed in every cycle; only the golden build's engine check, which talks to `localhost`, needs Windows
  `node.exe`.

## A known limit: the old lease's access token

root's access token from lease A, issued before the return, is answered on the same slot after the reset, by `23` and by
`12sp9` alike (measured here and added to `docs/e2e-12sp9.md`). The password it came from is dead and the OAuth server
refuses its refresh token, but the access token is a self-contained JWT (`accessTokenLifetime` 3600 s) signed with the
certificate every slot of the flavor copies from golden, naming root, whose id is the same in every restore of the golden
backup; nothing the reset restores holds it. So the previous leaseholder can act as root on the next lease of the same
slot until the token expires. Another slot refuses it: the token names its slot's database (`23-01`'s on `23-02`:
"Database configuration was not found for 'arashouse_23_01'"). The cycle records the probe as an observation, not a
check; a per-reset OAuth signing certificate is map ticket 54, which v1-readiness (ticket 51) waits on.

files deleted. So none of the eight lease passwords is in the broker's audit log or its service log either.
