# Acceptance: the lease cycle on the host for `35`

Ticket 52. Ticket 35's procedure (`docs/e2e-12sp9.md`) for flavor `35`: Release 35, server `14.35.0.43890`, libs-js
engine `14.35`, with ticket 36's 14.x OAuth checks (`docs/e2e-23.md`). The promise is the same, **a returned slot is
wiped, and the next lease is clean**. Before it, the 14.35 engine had met a live server only in spike 08 and in the
golden build's engine check (`docs/baselines.md`); this is its first run against a lease, and its first import.

## How it runs

`test/host/e2e-35.test.ts` runs `test/host/e2e-cycle.ts` twice in a row for `35`, only when asked (`ARASHOUSE_TEST_E2E=1`,
the variables are in its header), from WSL as the worker, non-elevated, against the installed broker. It is ticket 36's
cycle (`engine: "14.35"`, `oauthState: true`, `lockHolder: "worker"`) with one option more:

- `importOptions1435: true`: the 14.35-only import options (the libs-js README). Step 2 reads golden's languages. Step 3
  imports a second scratch package, `LIBSJS-SCRATCH-B-<TAG>`, with `--batch --batch-max 2 --collect-errors --max-errors 5`:
  five Variables, read in file order and sent two at a time, the fourth repeating the second's name. The server refuses
  the fourth, so its batch fails and falls back to one by one; the third is applied, the fourth's error is collected and
  the run goes on to the fifth. The cycle checks the summary (exit 1, `result: failed`, batch size 2, collect limit 5,
  errors), the log's fallback lines, and that each good Variable exists once, the fifth too. Step 6 checks that the four
  Variables and the package's definition are gone. When golden has a language besides `en`, the batch import also passes
  `--languages` with golden's codes; Release 35's golden has only `en`, so that import is recorded as not run.

Libs-js is import-export-libs-js `99c19b98`, the commit spikes 07, 08 and tickets 26, 36 used. Variable names are capped
at 32 characters by the server (`Property "Name" ... exceeds the maximum length of 32 characters`), so the batch items
are `AH-E2E-<tag>-B<n>`.

A `get` the cycle expects to lease at once now passes `--wait 900` (it was 300, ticket 36): in run 1 the other lanes'
leases kept the host's free RAM under `min_free_ram_mb` (2048) for more than five minutes.

## What the 14.35 engine did that the 12 SP9 runs never saw

For libs-js ticket 46 (live parity), not acted on here:

- **The login gate and version probe accept a live 14.35 server.** Every export and import named `server:
  14.35.0.43890` in its summary; the `14.35` engine's login gate (servers 12 to 14) let it through.
- **LP-040's version test met a live server, and answered false.** Each 14.35 import here read the live server's
  version (`14.35.0.43890`) for `NeedToHandleNullPropertyValues` and took its false branch: no null-value handling, so
  the `Property` branch of LP-042 stays off. Both imports passed. That branch matters only for a language pack's generated
  `Property` items (`context_action="lpimport"`), and the cycle imports no language pack (golden has only `en`), so what
  the false branch changes on the wire is still unproven against a server.
- **A failed batch is rolled back whole.** The batch of the third and fourth Variables failed on the fourth; the
  fallback's `add` of the third then succeeded, so the server had applied none of that `<AML>`. The engine's fallback
  (`IMP-516`) assumes nothing about it, and on this server it does not need to.
- **Aras 14.35 accepts an empty `<AML></AML>`.** The libs-js spec (`IMP-515`) says what Aras answers to the final
  flush of an empty queue is not known. In the exploratory run, whose last item was the refused one, the engine sent
  `<AML></AML>` and logged `AML successfully applied in AML batch mode` (batch time 8.9 ms): the server answers it
  without a fault. In the cycle the fifth Variable fills the final flush, so it is not empty.
- **Collected errors end the run as failed.** With an error collected the summary is `result: failed` and the exit
  code is `1`, not `2` ("done, but the engine sent at least one error message"), and the engine sets the package's
  release status to `failed`; every good item is in the database all the same.
- **The first export after a slot's start can be slow.** Run 1's first export of one ItemType took 59.9 s; every
  other took 8.1 to 9.8 s. The golden build's engine check, also the first request of its kind on a fresh instance, took
  56.2 s.

## The old lease's access token (fixed by ticket 54)

As on `12sp9` and `23` (`docs/e2e-23.md`): in ticket 52's runs, root's access token from the previous lease was answered
on the same slot after the reset, until it expired; the cycle recorded it as an observation.

Ticket 54 (2026-10-28) gives every slot its own OAuth signing certificate at each provision and reset (`docs/reset.md`),
and the cycle now checks both "the slot signs with a new OAuth certificate" (five copies of `OAuthServer.cer` in a `35`
slot, one certificate, not lease A's) and "the old lease's access token is refused". Both cycles of a run against that
broker passed every check (79 and 80 steps, `Test Files 1 passed`), the old token refused with `HTTP 401` each time;
the tree step took 5.0 to 5.4 s of resets of 48 to 52 s.

## The deny-list and the passwords
